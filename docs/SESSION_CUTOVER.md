# 세션 인증 전환

## 검토·출시 전

현재 출시 앱은 세션 토큰을 보내지 않는다. 서버가 이를 거절하면 앱이 로그인 정보와 온보딩 완료 기록을 지운다.

임시로 `ALLOW_LEGACY_API=true`를 사용한다. 미설정 시에도 같은 호환 모드가 적용된다. 이는 운영자가 승인한 기존 API 방식의 복원이며, 사용자 ID·인스타 ID만으로 접근하던 이전 방식의 보안 한계가 있다.

- 기존 사용자·알람·메시지·인스타 인증 API의 요청 형식을 지원한다.
- Authorization이 있으면 반드시 검증하며, 잘못되거나 만료된 토큰은 이전 방식으로 우회하지 않는다.
- 새 앱은 `X-Love-Alarm-Auth: session-v1`을 보내므로 토큰이 누락되어도 이전 방식으로 우회하지 않는다.
- 결제·열람권·메시지 잠금 해제·신고 관리 API는 계속 세션/관리자 인증이 필수다. 이전 메시지 API는 유료 메시지를 노출하지 않는다.
- 로그인 시 기존 JWT_SECRET을 재사용하는 수정과 mTLS 설정 로드 수정은 유지한다.

검토용 파일은 저장소 루트의 `love-alarm.ait`를 새로 빌드해 업로드한다. 업로드·검토 요청·검토 통과만으로 서버 호환 모드를 끄지 않는다.

## 새 빌드 출시 후

1. 검토를 통과한 세션 인증 빌드를 실제로 출시한다.
2. 토스 앱을 완전히 닫고 다시 열어 기존 계정 로그인, 재접속, 알람 목록, 메시지를 확인한다.
3. Render `love-alarm-server`의 환경변수 `ALLOW_LEGACY_API=false`를 저장하고 서버에 반영한다. 서버 코드나 토스 빌드를 다시 만들 필요는 없다. 환경변수 반영을 위한 서버 재시작/배포는 필요하다.
4. 토큰 없는 이전 요청은 401, 새 빌드의 정상 세션 요청은 200인지 확인한다.

기존 앱과 새 앱은 호환 모드에서 함께 동작하므로 출시와 서버 전환을 정확히 동시에 할 필요는 없다. 다만 이전 앱을 계속 사용하는 사용자는 호환 모드를 끈 뒤 차단되므로, 새 버전 적용을 확인한 다음 전환한다.

문제가 생기면 `ALLOW_LEGACY_API=true`로 호환 모드를 다시 켠다. 새 빌드의 인증 요청은 이 상태에서도 계속 검증된다. SESSION_SECRET/JWT_SECRET은 변경하지 않는다.

## 검증

`node --test backend/src/routes/legacy-api.test.js`는 운영 DB 없이 로컬 HTTP 서버로 기존 앱 재접속, 기존 로그인 수정, 이전 메시지 호환, 인증 우회 방지, 환경변수 전환을 확인한다. 테스트용 PostgreSQL이 필요한 기존 결제 통합 테스트는 `TEST_DATABASE_URL`이 별도로 있을 때만 실행한다.
