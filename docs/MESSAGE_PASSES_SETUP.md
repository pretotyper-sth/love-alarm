# 메시지 열람권 설정 및 출시

## 상품 등록

앱인토스 콘솔의 **좋아하면 울리는** 미니앱 → 인앱결제에서 **소모품** 두 개를 등록하고 노출을 켭니다. 혼술바 상품을 그대로 쓰면 안 됩니다. 결제 상품은 미니앱별로 발급됩니다.

- 메시지 열람권 1장: 최종 판매가 1,100원. 설명: 메시지 1개를 열 수 있어요. 보낸 사람은 익명으로 유지돼요.
- 메시지 열람권 5장: 최종 판매가 4,400원. 설명: 메시지 5개를 열 수 있어요. 남은 열람권은 다음 메시지에 사용할 수 있어요.

콘솔이 공급가 입력 방식이면 공급가 1,000원 / 4,000원에 해당하지만, **최종 구매 금액이 1,100원 / 4,400원인지 콘솔에서 확인**합니다. 앱은 SDK가 반환하는 실제 상품 가격을 구매 버튼에 표시합니다.

등록 후 발급된 실제 SKU를 서버 환경 변수에 넣습니다. 가짜 SKU나 혼술바 SKU로 대체하지 않습니다. 프런트엔드에는 상품 ID를 다시 빌드해 넣을 필요가 없습니다.

```env
MESSAGE_PASSES_ENABLED=false
TOSS_MESSAGE_PASS_SINGLE_SKU=<좋아하면 울리는 1장 상품 SKU>
TOSS_MESSAGE_PASS_BUNDLE_SKU=<좋아하면 울리는 5장 상품 SKU>
SESSION_SECRET=<32자 이상의 충분히 긴 무작위 비밀값>
ADMIN_API_TOKEN=<별도의 관리자용 무작위 비밀값>
ALLOW_MOCK_LOGIN=false
NODE_ENV=production
```

기존 배포에 16자 이상의 `JWT_SECRET`이 설정돼 있으면 세션 서명에도 재사용합니다. 신규 환경은 32자 이상의 `SESSION_SECRET`을 설정합니다. 명시적으로 잘못 설정된 SESSION_SECRET을 다른 키로 우회하지는 않습니다.

기존 토스 로그인용 mTLS 인증서를 재사용합니다. `TOSS_CLIENT_CERT_BASE64`와 `TOSS_CLIENT_KEY_BASE64` 또는 파일 경로 설정이 필요합니다. 비밀값은 `VITE_` 변수에 넣거나 커밋하지 않습니다.

## 적용 순서

1. 운영 DB를 백업하고 현재 스키마와 `backend/prisma/schema.prisma`의 기존 테이블이 일치하는지 확인합니다. 과거 DB push로 만든 VerificationSession도 필요합니다.
2. backend에서 `npm ci`, `npx prisma generate`, `npx prisma migrate deploy`를 실행합니다. 이번 마이그레이션은 기존 메시지·반응을 별도 수신함으로 복사하며 기존 메시지에는 과금하지 않습니다. 테이블 초기화나 `migrate reset`은 사용하지 않습니다.
3. 서버를 배포하고 SESSION_SECRET, SKU, mTLS 설정을 확인합니다. 새 서명 세션 도입으로 기존 사용자는 다시 토스 인증을 진행합니다. 일반 브라우저의 모의 로그인은 운영에서 차단됩니다.
4. 프런트엔드를 빌드하고 새 `.ait` 번들을 검토/배포합니다. 저장소 루트의 기존 `love-alarm.ait`는 과거 파일일 수 있으므로 이번 소스로 새로 빌드한 파일을 사용합니다.
5. QR로 토스 앱에서 실제 등록 상품 목록과 금액을 확인합니다. 실제 결제 검증은 과금이 발생할 수 있으므로 운영자가 직접 진행합니다. 샌드박스의 가짜 주문을 서버에서 실제 결제로 인정하지 않습니다.
6. 정책/환불 안내를 실제 운영 기준으로 확정하고 기기 검증 후 `MESSAGE_PASSES_ENABLED=true`로 켭니다. 두 SKU가 모두 설정되고 서로 다를 때만 새 메시지가 잠깁니다. 이 설정을 끄면 이후 도착한 메시지는 무료이며 이미 잠긴 메시지와 구매 권한은 보존됩니다. 판매가 중단돼도 미지급 구매 복원과 보유 열람권 사용은 가능합니다.

## 구매와 해제

- 받은 메시지가 기본 탭입니다. 서버에 저장된 Instagram 인증 내역으로 수신자를 판단하며 요청의 Instagram ID는 권한 근거로 쓰지 않습니다.
- 잠긴 메시지를 누르면 1장 / 5장 선택이 나오며 기본은 1장입니다. 구매 후 선택한 메시지에 1장을 바로 사용하는 것을 결제 전에 고지합니다.
- 토스 `processProductGrant`에서 서버 주문 조회를 완료한 뒤에만 지급 성공을 반환합니다. 구매자 `purchaserMatched === true`, 상품 SKU, 결제 완료 상태를 모두 확인합니다.
- 지급은 주문당 한 번, 사용은 사용자·메시지당 한 번입니다. 잔액·구매별 남은 수량·사용 원장·메시지 해제 권한을 한 트랜잭션으로 처리합니다.
- 앱 종료·네트워크 중단 후에는 로그인 시 미결 주문을 복원합니다. 구매 화면의 **구매 복원**으로도 재시도할 수 있습니다. 복원만으로 이전에 선택했던 메시지를 자동 차감하지 않습니다.
- 열기 전에 메시지가 삭제되면 차감하지 않습니다. 이미 연 본문은 수신함 사본으로 남기며 발신자의 알람 삭제/재등록이 구매한 본문을 바꾸지 않습니다.
- 잠긴 목록에는 본문과 발신자 계정 식별정보를 내려보내지 않습니다. 이전 메시지 본문 캐시는 제거하며 새 받은 본문을 localStorage에 저장하지 않습니다.
- 다시 보기와 이모지 반응은 무료입니다. 50개까지 최근 구매/사용 내역을 표시합니다.

## 신고 검토 및 환불

미열람 상태에서도 신고/숨김이 가능합니다. 신고는 서버에 저장되므로 다른 기기에서도 숨김이 유지됩니다.

- `GET /api/messages/reports`: 검토 대기 신고 최대 100개 조회.
- `POST /api/messages/reports/:id/resolve`, JSON `{ "uphold": true }`: 신고 인정. 유료로 연 메시지면 사용한 1장을 한 번만 복구. 무료 메시지나 이미 결제 환불된 주문에는 지급하지 않습니다.
- `{ "uphold": false }`: 신고 기각. 자동 복구 없음.
- 관리자 API는 `Authorization: Bearer <ADMIN_API_TOKEN>`이 필요합니다. 일반 사용자 세션으로는 실행할 수 없습니다. 이 비밀값을 앱에 넣지 않습니다.

열람권 복구와 금전 환불은 다릅니다. 금전 환불은 토스 콘솔/앱마켓의 구매 내역과 원장의 사용 내역을 확인해 처리합니다. 앱은 **이미 환불된 주문의 남은 열람권 회수**를 지원하며, 환불 신청이나 승인 자체를 자동 수행하지 않습니다. 구매 복원 시 환불 내역을 모든 페이지 확인하고 서버에 반영합니다. 메시지를 유료로 열기 직전에도 해당 열람권의 원주문을 서버에서 재검증하므로, 앱의 복원 호출을 건너뛰어도 환불된 열람권으로 본문을 열 수 없습니다.

미사용·부분 사용 시 금전 환불 기준, 신고 검토 응답 기한, 약관과 구매 전 안내는 실제 운영 정책으로 확정해야 합니다. 현재 일반 이용약관의 결제수단 문구도 인앱결제에 맞춰 업데이트해야 합니다.

## 검증

- `npm run test:message-passes`: 세션 변조·상품 검증·본문 비공개·클라이언트 지급/취소/복원 검사.
- backend `npm test`: 기존 Instagram 인증·DB 활동 검사 포함.
- `TEST_DATABASE_URL=<폐기 가능한 PostgreSQL DB> npm run test:message-passes`: 실제 HTTP API의 중복 지급·중복 사용·트랜잭션 롤백·다른 계정 접근 차단·신고 복구·환불 회수 검사. TEST_DATABASE_URL이 없으면 통합 검사만 건너뜁니다. 통합 테스트 전 현재 스키마를 별도의 테스트 DB에 적용합니다. 운영 DATABASE_URL은 자동으로 사용하지 않습니다.
- frontend에서 `npx vite build`로 웹 번들을 빌드합니다.

이번 작업에서는 실제 토스 결제, 운영 DB 이전, 운영 배포를 실행하지 않습니다. 콘솔 SKU가 없는 동안 구매 버튼은 비활성 상태입니다.
